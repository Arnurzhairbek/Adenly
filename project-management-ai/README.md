# AI-ассистент менеджера проекта: еженедельный статус

Выбранный процесс: подготовка проверяемого еженедельного черновика статуса по GitHub Issues и Deployments. Он повторяется, требует ручной сверки нескольких списков, а черновик можно проверить по ссылкам на первоисточники. Ассистент не меняет задачи и не публикует отчёт.

В этой рабочей папке проверялись две недели, заканчивающиеся датами двух GitHub milestones (`ЛЗ 7 — 2026-11-13` и `ЛЗ 7 — 2026-11-20`). GitHub не помечает эти milestones как спринты, поэтому периоды описаны как недельные окна, не как подтверждённые спринты.

## Что автоматизировано

`scripts/weekly_status.py` собирает созданные/закрытые за период issues, текущие открытые задачи с метками `in progress` и `blocked`, и GitHub Deployments со статусом. Python считает метрики; Ollama получает готовый JSON и только пишет текст. Скрипт сохраняет Markdown-черновик и JSON-факты.

Настраиваемые переменные: `GH_REPO=OWNER/REPOSITORY`, `GH_TOKEN` (необязателен для публичного репозитория; в Actions передаётся как read-only secret), `OLLAMA_URL` (по умолчанию `http://localhost:11434`), `OLLAMA_MODEL` (по умолчанию `qwen2.5:3b`), `IN_PROGRESS_LABELS`, `BLOCKED_LABELS`. Периоды трактуются как полуинтервал `[since, until)`, все даты UTC. Для приватного репозитория выдайте токену только необходимые разрешения чтения Issues и Deployments; используйте отдельный минимально привилегированный fine-grained token.

## Локальный запуск

1. Установить Python 3.12+, `pip install -r requirements-ai.txt`, Ollama и модель `ollama pull qwen2.5:3b`.
2. Для приватного репозитория задать переменные только в текущей PowerShell-сессии (токен не записывать в код); публичный репозиторий можно читать без `GH_TOKEN`:

   ```powershell
   $env:GH_TOKEN = '...'
   $env:GH_REPO = 'OWNER/REPOSITORY'
   ```

3. Для недельного отчёта: `python scripts/weekly_status.py`.
4. Для исторического периода: `python scripts/weekly_status.py --since 2026-01-01 --until 2026-01-15 --prompt-version v1`.
5. Чтобы получить только проверяемые факты без модели (например, если Ollama ещё не установлена): `python scripts/weekly_status.py --since 2026-01-01 --until 2026-01-15 --facts-only`.
6. Чтобы повторить генерацию на том же зафиксированном наборе фактов, например сравнить v1/v2/v3: `python scripts/weekly_status.py --facts-file project-management-ai/facts/facts_20261107_20261114.json --prompt-version v1 --no-record-run`.
7. Проверить числовые поля v3 по facts JSON: `python scripts/verify_weekly_status.py --facts-file project-management-ai/facts/facts_20261107_20261114.json --report project-management-ai/reports/weekly_status_20261107_20261114.md`.
8. Черновик попадёт в `project-management-ai/reports/`, проверяемые исходные факты — в `project-management-ai/facts/`. Время сбора+генерации автоматически добавляется в `measurements/automation_runs.csv`; PM вручную вносит фактическое время полной проверки и правки после каждого отчёта. Ответственный PM сверяет каждое утверждение и только затем переносит одобренный текст в командный канал. Исторический статус задач реконструируется по датам создания/закрытия; labels отражают текущее состояние, поскольку GitHub REST issue list не предоставляет историю labels на дату отчёта.

У GitHub-hosted runner есть собственный `localhost`, он не видит Ollama на ноутбуке. Workflow запускает Ollama на runner на время задачи; отчёт сохраняется как Actions artifact, а не коммитится автоматически. GitHub токен хранится в repository secret `GH_TOKEN`. Workflow требует, чтобы этот проект был опубликован в GitHub и Actions были включены.

## Роли и контроль

- Владелец автоматизации следит за Actions, зависимостями и доступом к токену.
- Назначенный PM проверяет **каждое утверждение** черновика по сохранённому JSON и ссылкам GitHub; фиксирует время, правки и ошибки в `audit/claim_audit.csv`.
- До проверки это внутренний черновик. После проверки PM публикует его в согласованное место команды и добавляет ФИО проверившего в раскрытие ИИ.

## Запрещённые данные

- Пароли, токены, ключи, cookie: секреты доступа; не помещать в issue title/labels, prompt или отчёт.
- Персональные и чувствительные данные сотрудников/клиентов: не нужны для агрегированного статуса и создают риск приватности.
- Данные клиентов, коммерческие тайны, уязвимости до раскрытия и закрытые инциденты: могут причинить ущерб при передаче модели или артефактам CI.
- Исходный код, содержимое приватных комментариев и вложения: для метрик не нужны; скрипт намеренно не загружает bodies/comments.
- Если заголовки задач содержат чувствительные данные, не использовать Ollama на общем/внешнем runner; сначала обезличить заголовки или отключить отправку их в prompt.

## Кандидаты и отклонённое

- Оценка сроков и вероятности выполнения — отклонено: низкая проверяемость и цена ошибочного уверенного прогноза высока.
- Автоматическое назначение приоритетов — отклонено: требует бизнес-контекста и может менять решения команды.
- Протокол встречи — отложено: нет стандартизированного источника записей и согласованного процесса обработки персональных данных.
- Список «зависших» задач как отдельная автоматизация — отклонён: простой фильтр по `updated_at` решает задачу без модели. Его можно добавить как проверяемую метрику в дальнейшем.

## Измерения, точность и окупаемость

Заполнить `measurements/manual_baseline.csv` тремя секундомерными ручными замерами до сравнения. Запустить на двух прошедших спринтах, для каждого заполнить `measurements/automation_runs.csv` временем генерации, сплошной проверки и правки. Проверить каждое предложение; журнал ошибок хранить в `audit/claim_audit.csv`. Сравнить v1 и v2 на одинаковых фактах, считать долю существенных и стилистических ошибок отдельно.

Пока у рабочей папки нет Git remote и GitHub подключение требует повторной авторизации, поэтому реальные отчёты и аудиты не созданы. Не подменять их примерами. Сроки спринтов, три замера, часы разработки, проверяющий и фактические ошибки должны быть внесены командой по наблюдениям.

Формулы: `среднее ручное время = A`; `чистая экономия на отчёт = A - (генерация + проверка + правка)`; `чистая экономия на цикл = чистая экономия на отчёт - обслуживание`; `окупаемость в циклах = часы разработки * 60 / чистая экономия на отчёт (мин)`, только если знаменатель > 0. Для окупаемости в неделях умножить циклы на 1 неделю. Отрицательная экономия означает, что финансово-временная окупаемость не подтверждена.
